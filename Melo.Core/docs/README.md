## 当前架构：三个进程

```
UI 进程（语言自由，建议 C# + Avalonia）
    ↕  跨进程协议（控制 JSON / 大数据共享内存）
核心进程（实现语言自由）
    ↕  跨进程协议（控制 JSON / 音频共享内存环）
插件进程（语言自由）
```

**两道协议共用一套协议内核**——消息框架、序号、取消、回压、错误帧写一遍两处用。
**核心层契约与语言无关**。可以存在多个等价实现；单个实现内部的语言与 FFI 选择不进入公共契约。

---

## 已确认的架构约束

1. **核心层独立进程，实现语言自由**；各语言实现共用规范、一致性测试和性能场景
2. **UI 层语言自由**，起步建议 C# + Avalonia
3. **插件层独立进程**，语言自由
4. **有界面插件自带界面**，不绑定 Vue 或任何框架
5. **无界面插件的参数面板**由核心转发声明、UI 渲染
6. **音频合成不走序列化**，走共享内存环
7. **两道协议共用一套协议内核**，UI 与插件在协议层平权
8. **协议层收敛为两道**（原图画了三道；「插件接口 / 引擎接口」是契约声明，不是协议）

---

## 四个最重要的结论

**① 边界判据只有一条：这份数据是否需要「求值」？**

要 → 归核心层（波形峰值、曲线折线、音符矩形）；不要 → 归 UI 层（缩放、滚动、hover）。
守不住这条，协议层会退化成远程过程调用总线。

**② UI 层整体可替换——这是本次架构变更最大的收益。**

核心层跨进程后，卷帘拿的是协议 payload，不再直接摸核心层数据结构，
所以那条绑定链断了。**换 UI 的成本是"写一个客户端"，不是"重写项目"。**
（旧方案同进程时结论是"只有一半能换"，因为自绘卷帘直接读核心层的峰值金字塔和插值能力。）

**③ 代价是每帧过路费——必须用共享内存抵掉。**

卷帘滚动一帧 30KB，走 JSON 序列化撑不住 60fps。**共享内存不是优化项，是硬要求。**
另外跨边界后 trace/重放从"可选优化"变成"必需基础设施"。

**④ 核心层语言不预先选定。**

Rust、C++、C#、Go、Zig 等实现用相同的黑盒一致性测试和实时性能指标比较。
实时线程的“不等待、不分配、不调用插件”是实现约束，不依赖某一种语言的宣传特性。

## 与 TuneLab 的关系

| | TuneLab | v3 新架构 |
|---|---|---|
| 核心层语言 | C#（被迫） | **不限定，可维护多个等价实现** |
| 音频线程 GC | 要手工规避 | **由具体实现处理，并统一通过实时验收** |
| UI 可替换 | ❌ | **✅** |
| 性能路径 | 函数调用（最短） | 跨进程 + 共享内存（约 10 倍） |
| 每帧过路费 | 零 | **固有** |
| 调试难度 | 低 | **高（需 trace/重放）** |
| 契约保障 | 编译期（RS0016） | **运行时（需自建闸门）** |
| 插件面板能力 | 12 种控件封死 | **无上限** |
| 多客户端 | 不支持 | **平权客户端** |

> **一句话**：TuneLab 用编译期约束换运行时确定性和零拷贝；
> 新架构用运行时复杂度和每帧过路费，换语言自由、UI 自由、插件自由。
> **不是谁更好，是拿"确定性和性能"买"解耦和自由度"。**

**若不做多端**，建议先按"核心层同进程"起步，但把协议层预留出来
（接口按协议形状定义，先走进程内直调）。将来要做多端时把核心层抽出去独立进程即可。
