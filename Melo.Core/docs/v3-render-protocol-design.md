# v3 渲染协议层设计（核心引擎 → UI 层）

> **后续设计**：本文为渲染协议初稿。跨进程资源描述符、视口坐标、渐进帧、回压与生命周期
> 的具体化见 [`core-architecture.md`](core-architecture.md) §6；原文冲突与波形公式修正见该文 §12。

> **目标**：核心引擎负责重算波形、参数曲线、音符等数据，经本协议层把「界面绘制所需的全部数据」统一交给 UI 层。
> UI 层只做接收与渲染，不做任何业务求值。
>
> **本文的定位**：这是 v3 方案内部的落地设计。文中每条"参考实现"都指向 TuneLab 现有代码，
> 用意是**把已经踩过的坑直接搬过来**，而不是从零发明。凡标注「来自 TuneLab」的机制，都是在
> 生产代码里跑通的；凡标注「v3 需自行解决」的，是跨边界带来的新增成本。
>
> **前置约束**（见 [`v3-architecture-decision.md`](v3-architecture-decision.md)）：
> - **核心层独立进程**，实现语言自由；多个实现遵循同一协议与一致性测试
> - **UI 层独立进程**，语言自由
> - **插件层独立进程**
> - 两道跨进程协议**共用一套协议内核**，大数据一律走共享内存
>
> 因此本文描述的所有跨边界传递**都是真正的跨进程传递**——没有"同进程可直接引用"
> 这条捷径。§3 的通信方式、§5.1 的一致性、§6 的性能预算都按这个前提写。

## 0. 先划清一条边界：什么算"渲染数据"，什么不算

这是整份设计里最容易被做错的一步。**不是所有 UI 用到的东西都该进协议层。**

判据只有一条：**这份数据是否需要"求值"才能得到？**

| 类别 | 是否需要求值 | 归属 | 例子 |
|---|---|---|---|
| **计算结果**（波形峰值、参数曲线折线、合成音素、音符矩形） | 要——依赖音频样本、曲线插值、tempo 换算 | **走协议层**，核心层算完再给 | `Waveform.Peak[]`、`GetValues(ticks)` 的结果 |
| **视图几何**（缩放、滚动位置、像素↔tick 换算） | 不要——纯当前视口的函数 | **留 UI 层**，核心不知道也不需要知道 | `TickAxis.Tick2X` |
| **交互反馈**（hover 高亮、拖拽预览线、光标） | 不要——纯 UI 瞬时状态 | **留 UI 层**，不进核心 | 连线预览、dirty 高亮 |
| **结构元数据**（有哪些轨、轨的显隐、量程、颜色） | 不要——声明期就定了 | **走协议层，但只在结构变化时推** | 轨清单、`AutomationConfig.Scale/Color` |
| **用户数据**（锚点、音符本体） | 不要——就是数据本身 | **走协议层**，但它同时是编辑入口 | `IPiecewiseAutomation` 的锚点组 |

**为什么这条边界必须一开始就划清**：v3 的图里，核心层同时画了「播放引擎 / 调度引擎」和
「撤销 重做 选区 保存 加载 导出」。如果让 UI 层把这些也当"数据"接过来渲染，协议层会立刻退化成
一个**远程过程调用总线**——那就不是渲染协议了。所以下面所有设计都严守一条：

> **协议层只传"画什么"，不传"怎么画"，也不传"帮我做件事"。**
> （写操作另有一条通道，见 §6，两者不混用同一种消息。）

## 1. 接口定义

### 1.1 两种数据形状：快照（Snapshot）与句柄（Handle）

这是控制拷贝量的核心决定。所有跨边界的数据只有两种形态：

- **快照**：值语义、只读、一次性。适合小而高频的数据（音符矩形、峰值数组）。
- **句柄**：引一个不变对象 + 一个版本号。适合大而低频的数据（整段音频、整条曲线）。
  句柄的语义是「**发布即不可变，变化时换引用**」。

```csharp
// 每个句柄都带版本号，UI 侧缓存键就是它。
public readonly record struct DataHandle<T>(T Value, long Version);
```

这条「发布即不可变」的纪律是**整个性能方案的地基**，不是可选项。它带来两个直接好处：

1. UI 层拿到句柄后可以放心在自己的线程上慢慢画，核心层下一帧换新引用不会改到它手上那份；
2. 缓存判等只需比版本号，不需要深比较。

> **来自 TuneLab 的实证**：`SynthesisLock.CaptureSynthesizedParameter` 的注释写得很直白——
> 「**必须冻结**：笔刷第一帧写入就会触发合成失效、引擎可能随即清掉该区产物，后续帧再读实时产物
> 就是空的，整笔会什么都写不进去。产物按 SDK 契约『发布即不可变、变化时换引用』，故持旧引用安全。」
> 这条纪律在 TuneLab 里是**已经在救命的**，不是纸面原则。

### 1.2 请求：视口即唯一入参

UI 层要数据时只发一个东西——**它当前看得见什么**。核心层据此决定算多少。

```csharp
// UI → 核心：我要这一块的数据。整个协议里最重要的一个结构。
public sealed record ViewportRequest
{
    public required ViewportId Target { get; init; }   // 编排区 / 钢琴窗 / 某条参数轨
    public required double MinTick { get; init; }      // 可见 tick 区间（全局 tick 域）
    public required double MaxTick { get; init; }
    public required double PixelsPerTick { get; init; }// 缩放：决定采样密度
    public required double DisplayHeight { get; init; }// 参数轨/波形的高度：决定纵向采样
    public long Generation { get; init; }              // 请求序号，用于丢弃过期回答
}
```

**`PixelsPerTick` 必须进请求，不能由核心层猜。** 因为它直接决定采样密度：视口宽 800px 时，
逐像素采样就是 800 个点，与 tick 跨度无关。核心层若按固定 tick 步长算，缩放后会立刻出现
要么锯齿、要么浪费（放大后点太稀 / 缩小后点太多）。

> **来自 TuneLab**：`AutomationRenderer.OnRender` 里就是 `int n = (int)Math.Ceiling(Bounds.Width / step)`
> ——**按像素数决定采样点个数**，再逐点 `TickAxis.X2Tick(xs[i])` 换成 tick 去求值。
> 这正是"采样密度由视口决定"的写法，直接对应协议里的 `PixelsPerTick`。

### 1.3 回答：按图层分槽，每槽独立版本

```csharp
public sealed record ViewportPayload
{
    public required ViewportId Target { get; init; }
    public required ViewportRequest Echo { get; init; }       // 回显这是哪个请求的答案
    public required IReadOnlyList<LayerData> Layers { get; init; }
    public bool IsFinal { get; init; }                        // 是否已落定（见 §5 的渐进推送）
}

public sealed record LayerData
{
    public required LayerKind Kind { get; init; }             // Waveform / Curve / NoteBlock / ...
    public required long Version { get; init; }               // 该槽内容的版本，未变则复用它
    public required object Payload { get; init; }             // 具体见 §2 各图层
}
```

**为什么按图层分槽而不是一个大对象**：一次编辑往往只影响一类数据。改了 gain 参数曲线，
波形、音符块都没动——分槽之后那两个槽的版本号不变，UI 层直接复用上帧的绘制结果。
一个大对象则会让"只变了一项"也触发全量重传。

## 2. 三种渲染数据的组织格式

### 2.1 波形：金字塔峰值 + 视口自适应

**不能传原始样本。** 44.1kHz 立体声一分钟是 500 万个 float（20MB），跨边界传一次就完了。

正确的形状是**多级峰值金字塔**，每级按 hop 取 min/max：

```csharp
public struct Peak          // 一个像素列要画的那根竖线
{
    public float Min;         // 下限
    public float Max;         // 上限
    public double MinRatio;   // min 落在这一列内的相对位置 [0,1]（画包络的"插值细节"）
    public double MaxRatio;
}

public sealed record WaveformLayer
{
    public required IReadOnlyList<Peak> Peaks { get; init; }  // 长度 = ceil(可见像素宽度)
    public required int PeakHop { get; init; }                // 这一级金字塔的 hop
}
```

**金字塔分级**：预建 hop = 64 / 256 / 1024 / 4096 … 各级。请求时按
`PeaksPerPixel = PixelsPerTick⁻¹ × (每秒 tick 数) ÷ 采样率` 选**最接近但不小于**所需密度的那一级，
再在该级上做窗口合并。这样无论用户缩到全曲还是放到单个音符，**参与计算的峰值数量都 ≈ 可见像素数**，
与总时长无关。

> **来自 TuneLab**：`TuneLab/Audio/Waveform.cs` 就是这个结构。构造函数收 `peakHop = 64`，
> `UpdatePeak` 预建 `mPeaks`（每 hop 一个 `PeakInfo{min,max,minIndex,maxIndex}`）；
> `GetPeaks(positions, values)` 收**逐像素的坐标数组**，对每个像素列汇总——
> 若该列只横跨一个 hop 就直扫样本，跨多个 hop 就把中间的 hop 峰值并进来
> （`for (int pi = lastPi + 1; pi < nextPi; pi++)` 那一段）。
> `MinRatio/MaxRatio` 是为绘制时把那根竖线的端点摆准用的，不是可选的装饰。

**一个重要细节**：峰值缓存要**按 hop 增量维护**，不能每次重建整条。TuneLab 的 `UpdatePeak(startIndex, endIndex)`
就是增量接口——合成完成一段就只更新那一段的 hop 桶。

### 2.2 参数曲线：逐像素折线 + NaN 断开

曲线的形状由求值域决定，而求值必须发生在核心层（引擎产物在**秒域**，用户锚点在
**part-local tick 域**，中间要过 tempo 换算）。

```csharp
public sealed record CurveLayer
{
    public required IReadOnlyList<double> Xs { get; init; }   // 逐像素，已换算完毕
    public required IReadOnlyList<double> Ys { get; init; }   // 值；NaN = 此处断开
    public required bool HasNaN { get; init; }                // 有 NaN 时 UI 才走"分段"绘制路径
}
```

**关键约定：用 NaN 表达"此处无值"，不用额外的分段数组。**

因为 `NaN` 在绘制端天然映射成"断笔"，而"有没有值"这件事在**引擎语义里本来就是 NaN 承载的**：

> **来自 TuneLab 的实证**：`AutomationConfig.DefaultValue` 是否 `NaN` 就是
> **连续轨与分段轨的区分判据**（`plugin-development` 体系里 `GetAutomationConfigs` 的注释原文：
> "连续轨与分段轨同在此 map，由 `AutomationConfig.DefaultValue` 是否 NaN 区分形态"）。
> 分段轨段间就是 NaN，`OnRender` 里的 `DrawPiecewise` 靠它断开不连线。

所以协议层不需要发明第二套"有没有值"的表达——直接把引擎本来就用的 NaN 透传过去，语义完全对齐，
也不会出现"协议说无值、数据说 NaN"两套真相。**UI 侧只需判断 `HasNaN` 决定走不断笔的快速路径。**

**三种轨的绘制语义要在协议层显式标注**，不能让 UI 猜：

| 轨形态 | 协议字段 | UI 画法 |
|---|---|---|
| 连续轨（含 vibrato 后的最终值） | `CurveKind.Continuous` | 处处有值，一条 polyline |
| 分段轨（段间 NaN） | `CurveKind.Piecewise` | 遇 NaN 断笔，多段 |
| 二值区间轨（`IsBand`） | `CurveKind.Band` | **不是折线**——画满高色带 |
| 逐 note / 逐音素 lane | `CurveKind.LaneSegment` | 顶线 + active 时半透明柱 |

> 这四种正是 TuneLab `AutomationRenderer.OnRender` 里 `Draw` 闭包的四个分派分支
> （`IsEffectiveNoteLane` / `IsEffectivePhonemeLane` / `IsEffectiveAutomation` /
> `IsEffectivePiecewiseAutomation` + `IsBand()`）。**这个分派必须留在核心层**：
> 判据本身要查 part 的有效轨集合，UI 层不该知道"什么叫 effective"。

### 2.3 音符：区间矩形 + 不变量已由核心保证

```csharp
public sealed record NoteBlock
{
    public required double StartTick { get; init; }
    public required double EndTick { get; init; }     // 已去重叠、已内缩缝，UI 直接画
    public required int Pitch { get; init; }
    public required double Y { get; init; }           // 已换算成显示 Y
    public required double Height { get; init; }
    public required long NoteId { get; init; }        // 供 UI 侧做交互选中映射
    public required bool IsSelected { get; init; }
}
```

**核心层必须把几何算完，UI 层不做任何裁剪/去重/内缩**。理由：

> **来自 TuneLab**：`NoteLaneRanges(Part)` 负责去重叠；`OnRender` 里
> `double right = TickAxis.Tick2X(endTick) - 1;   // 1px 缝` 是防止相邻 note 连成一面墙。
> 这类"1 像素缝"如果交给 UI 层各自实现，不同视图之间必然不一致。

**`IsSelected` 走协议而不是走独立查询**：因为选中态变化是**高频**的（拖框选时每帧都变），
单独发一条"选中集变了"的消息会引入一次额外的跨边界往返。放进 payload 里跟其他数据一起走，
反正那一帧本来就要推。

**`NoteId` 是必要的**：UI 层要把点击位置映射回"哪个音符"，必须有稳定 id。
v3 里这条要额外注意——如果音符 id 由核心生成，UI 层不能自己用下标（列表一变就错位）。

## 3. 通信方式

### 3.1 分层建议

> **⚠️ 本节已按"核心层独立进程"的架构更新。** 早前版本假设核心层与 UI 同进程，
> 主张"插件引擎不跨协议边界"；插件改为独立进程后那条不成立，现改为
> **"跨边界但走共享内存，不走序列化"**。详见 `v3-architecture-decision.md` §3.3。

v3 的图上有三处"通信协议层"。**两道跨进程协议共用一套协议内核**，
但两条通道的配置不同，按数据特征分开选：

| 通道 | 特征 | 大数据走哪 | 控制走哪 |
|---|---|---|---|
| 核心 ↔ UI（**本文主角**） | 每帧、大数据、请求-响应 | **共享内存 + 固定布局** | JSON |
| 核心 ↔ 插件引擎 | 音频块级、硬实时 | **共享内存环** | JSON |
| UI ↔ 插件界面 | 低频、小消息、事件式 | — | WebView `postMessage` / 本地 WebSocket |

**共用协议内核**：消息框架、序号、取消、回压、错误帧——写一遍，两处用。
这样 UI 客户端和插件客户端在协议层是平权的，新增客户端类型不改架构。

### 3.2 消息形态：请求-响应 + 单向推送，两种

```csharp
// ① UI 主动要：拉模式（拉的是"当前该画什么"）
ViewportPayload RequestViewport(ViewportRequest req);

// ② 核心主动推：数据变了，且 UI 当前视口与脏区相交
void OnDataInvalidated(InvalidationNotice notice);

// ③ 渐进推送：大范围计算的中间结果（见 §5.2）
void OnPartialPayload(ViewportPayload partial);
```

**为什么必须有 ②**：纯拉模式（UI 每帧轮询）在空闲时会白白跑一遍求值。纯推模式则会在
"数据变了但用户此刻没看那块"时白算。**两者都要**：核心知道"哪块数据脏了"，UI 知道"我在看哪块"，
只有**交集非空**才值得算。这就是 ② 的判据。

### 3.3 最重要的一条：插件音频流不要走序列化

v3 图里「核心层 ↔ 插件层」也画成了经"通信协议层"。**这道边界是真实的**（插件是独立进程，
躲不掉），但它的**实现方式不能和 UI 通道一样**：

音频合成回调是**实时**的——引擎的 `CreateSession` / 合成调用会在音频线程或高优先级任务上跑。
如果中间隔一层序列化协议（编码 + 跨边界 + 解码），延迟抖动会直接变成爆音。

> **来自 TuneLab 的实证**：`IVoiceSynthesisEngine` 的契约注释写明
> `VoiceSourceInfos` "**必须立即返回、不得阻塞**——宿主与 UI 同步读取、无异步等待"。
> 这类接口的存在说明：**插件引擎面必须保持最低开销**。同进程时它是函数调用；
> 跨进程后无法回到函数调用，那就必须退到下一个最优解——
> **共享内存环 + 无锁**，而不是最差的解——消息序列化。

**所以最终形态是**：

- **控制指令**（建会话 / 改参数 / 报状态）：走消息通道，JSON，量小频低，性能不是问题
- **PCM 音频**：走共享内存环，双方按固定布局读写，**一次序列化都没有**
- **数据形状固定**：float32 平面或交错，格式在会话建立时协商一次

**一条建议**：播放引擎放在核心进程、直接独占音频设备。这样音频回调全程在核心进程内，
**一次跨进程都没有**——恰好绕开了独立进程架构最大的代价。

## 4. 更新触发时机

### 4.1 三类触发源

```csharp
public enum InvalidationKind
{
    Structure,   // 成员增删/签名变化：轨多了、音源换了、音符增删 → 必须重算拓扑
    Values,      // 仅值变：锚点移动、音符音高变 → 重算数值、拓扑不变
    Viewport,    // 视口变：滚动/缩放 → 数据没变，只是要看别的部分
}
```

这三类的**代价差着数量级**，绝不能混为一谈：

- `Viewport` 最便宜（可能命中缓存，因为旁边那块刚算过）；
- `Values` 中等（只重算脏区）；
- `Structure` 最贵（轨清单/绘制顺序都变了）。

### 4.2 合并：一拍内的多次变化只算一次

**这是整个性能设计里最有效的一招。** 一次拖动会连续产生几十次 `Values` 变更，
若每次都算一遍曲线，帧率必然崩。做法是**边沿触发 + 合并**：

```csharp
// 语义（与 TuneLab 的 ViewRefreshScheduler 完全一致）：
//  - 首次标脏排一次 flush；脏期间的后续标脏被吸收（不做每帧轮询，空闲零开销）
//  - 两级脏位：Structure 高于 Values；Structure 被标上时 Values 天然被覆盖
//  - 先清脏位再跑回调，回调抛异常不会把调度器锁死
//  - Suspended：拖动/键入期间抑制重建，避免打断交互；置回 false 时若有脏立即补排一拍
class RefreshScheduler
{
    void InvalidateStructure();   // → 下一拍整体重建
    void InvalidateValues();      // → 下一拍轻刷新（仅值变时）
    bool Suspended { get; set; }  // 编辑进行中抑制
}
```

> **来自 TuneLab**：`TuneLab.GUI/GUI/ViewRefreshScheduler.cs` 跟这个形状逐条对应。
> 它的类注释把两条纪律写得极清楚，值得直接抄：
>
> 1. **「订阅回调里只调 Invalidate*、不读数据——所有读取集中在 rebuild / refreshValues 回调内。」**
>    因为回调总在引发事件的数据操作整体结束后的下一拍执行，读到的是 settled 状态，
>    于是"按旧结构快照读已变化数据"的越界窗口**在结构上不存在**，无需在各订阅点写结构守卫。
> 2. **「两级脏位：Structure 高于 Values。'仅刷值'只在本拍结构干净时执行。」**
>    所以值回调按构建时结构读数据是安全的——任何结构变化必然已在同一拍把 Structure 标上。
>
> 这两条正是 §5.1 数据一致性方案的全部内容。**别自己另发明一套**。

### 4.3 脏区：能收窄就收窄，收窄不了就多算

对参数曲线，一次编辑真正影响的范围可以**精确算出来**——因为曲线插值是有紧支撑的：

```csharp
// 锚点编辑的脏区累加器：一次编辑波及 [i−k, i+k] 锚点跨度，k 由切线是否被钳零决定
class DirtyRange
{
    void Touch(anchors, index);       // 增/删/改：某锚点自身变了
    void TouchGap(anchors, index);    // 只有邻接关系变了（插入缝/删除缝）
    void CloseTails(anchors);         // 收口端点平延
    double Start, End;                // 并集
}
```

判据的数学基础（**直接决定能省多少**）：

- 若曲线是 **Monotonic Hermite 插值**，段 `[Pj, Pj+1]` 的取值由
  `(Pj, Pj+1, mj, mj+1)` 决定，而切线 `mj` 只依赖 `Pj−1 .. Pj+1`
  → 动一个锚点最远波及 **±2** 个锚点跨度。
- **可收窄的第一档**：切线被钳为 0 的锚点（两侧割线异号 / 有一侧为 0 ⇒ 极值或平台端；端点恒 0）
  与其外侧邻居**解耦**——`Pi` 怎么动它还是 0，那一侧的外区间纹丝不动。
- **可收窄的第二档（更强）**：**等值相邻**。两个等值锚点之间恒为常数（该侧割线为 0 ⇒ 两端切线皆钳零），
  于是那一段**连自己都不脏**，边界收回本点。"在等值的两点之间画一小段线不再波及两点之间的全部"。
- **相位纪律**：判据必须**变动前后都成立**，否则会漏掉"前非极值、后成极值"这类
  切线由非零变 0 的失效。实现上不比较两个状态——**每次入账各按当时几何判定，调用方在改动前后各入账一次**，
  并集自然等价于"前后都恒 0 才收窄"。**收窄与相位纪律是一体的**：未补齐相位的调用方
  必须走保守口径（恒 ±2，不收窄），"宁多勿漏"。

> **来自 TuneLab**：`TuneLab/Data/AnchorDirtyRange.cs` 就是这个类，上面每条规则都出自它的文档注释。
> 特别值得抄的一句：**"收窄因此与相位纪律是一体的——未补齐相位的调用方必须走保守口径（恒 ±2，不收窄）"**。
> 分段轨就是走保守档的（`PiecewiseGroup()` 恒 ±2），因为它的相位纪律没补齐。

**端点平延是独立的第三条规则**，别混进上面两条：首/末锚点之外按端点值平延至无穷，
该侧是否失效**只由端点的 (Pos, Value) 前后比较决定**（`CloseTails`）。
值变 ⇒ 整侧到无穷；仅位置变 ⇒ 只脏位移覆盖的那一段。

## 5. 数据一致性

### 5.1 一致性靠"单写者 + 一拍延迟"，不靠锁

**核心原则：数据变更只发生在核心层，且总是在一个"整段操作"结束后才对外可见。**

三层保障：

1. **订阅回调只标脏、不读数据。** 见 §4.2。这样"按旧结构读新数据"这类越界窗口在结构上不存在。
2. **版本号单调递增。** 每个句柄带 `Version`，UI 层记住自己上次渲染的版本；落后就重取，
   领先（收到了过期回答）就丢弃。
3. **请求序号 `Generation` 丢弃过期回答。** 快速滚动会发出多个请求，回答可能乱序到达；
   UI 层只认**最新 `Generation`** 的回答。这不是可选的优化——没有它，慢的旧回答会覆盖新画面。

**关于锁**：不要用锁来保护跨边界的数据。用**不可变快照 + 换引用**（§1.1）。
锁会把核心层的计算卡住 UI 渲染线程，而换引用的开销是一个指针赋值。这是"共享内存"能安全用在同一进程
两个组件之间的前提。

### 5.2 渐进推送：大范围计算不要等全部算完

长音频段（比如用户缩到全曲）的波形计算可能几十毫秒。等算完再交，UI 会卡一下。
正确做法是**分批推进度**：

```csharp
// 先给一个低分辨率粗视图（立刻能画），再逐块补细节
// IsFinal = false 的那几帧：UI 先画出来，标一个"还在算"的角标
// IsFinal = true：替换为完整结果
ViewportPayload { IsFinal = false, Layers = [粗峰值] }
ViewportPayload { IsFinal = false, Layers = [粗峰值 + 第一块细节] }
ViewportPayload { IsFinal = true,  Layers = [完整峰值] }
```

**这条在 TuneLab 里的对应物是合成状态带**：`SynthesisStatusStrip` 会把"哪段在算、哪段算完了"
画出来，而不是让用户对着空白等。**"让等待可见"比"假装没在等"重要**——尤其在外部驱动
（agent / CLI）的场景下，静默的慢比可见的慢更难排查。

> 这条也与 TuneLab 的一处文档纪律同源：`command-surface.md` 里明确
> 「**"让卡住这件事可见"**」——`VoicesManager` / `InstrumentsManager` 的 `Destroy`
> 逐引擎把"正在拆谁"写进日志，原因注释写着"宿主无从分辨'慢'与'卡'，
> 而静默的损坏比挂住更糟"。

### 5.3 一致性里最容易漏的一条：跨视图同步

同一个时间轴可能同时显示在**编排区**和**钢琴窗**两个视图里。
`editor reveal` 类操作必须**两个一起挪**——TuneLab 的注释点明了原因：

> 「编排区与钢琴窗的时间轴一起走（同 `transport.gotoStart`，**只挪一条的话用户在另一个窗里
> 看到的还是原处**）。」

**协议层要为此负责**：视口状态不能由各视图各自持有，必须有一个**共享的时间轴视图状态**
（`TickAxis` 那一份），两个视图都从它读。否则两个窗口会显示不同的时间范围——
这类 bug 用户一眼看得见，但排查时很难归因。

## 6. 渲染性能

### 6.1 性能预算：每一帧都在花谁的时间

| 环节 | 目标 | 手段 |
|---|---|---|
| 求值（核心层） | 与**可见像素数**成正比，与总时长无关 | 峰值金字塔分级 + 逐像素采样 + 脏区收窄 |
| 跨边界传递 | 每帧 < 1ms | 句柄换引用；只传变化的槽；大块用共享内存 |
| UI 绘制 | 60fps | 槽版本未变则复用上帧绘制结果（不重算不重传） |
| 空闲 | 零开销 | 边沿触发调度，不做每帧轮询 |

**"与总时长无关"是这里唯一真正的设计目标。** 一个三小时的有声书项目和一个十秒的测试片段，
滚动起来的开销必须一样。§2.1 的金字塔和 §2.2 的逐像素采样都是在保证这一条。

### 6.2 三条不能省的优化

1. **按像素采样，不按 tick 采样。** 见 §1.2。这是最容易写错的一个——按 tick 固定步长写出来
   在测试时（小工程、未缩放）往往看不出问题，上线遇到大工程才暴露。

2. **绘制时先判"能不能跳过"，再判"要不要重画"。** 一个三小时的工程有几千个音符块，
   视口里通常只有几十个。核心层**在生成 payload 时就该按可见区间过滤**，
   而不是把全部音符传给 UI 让 UI 裁剪。省的是跨边界的数据量，不只是绘制时间。

3. **结构变化与值变化分开处理。** 见 §4.2。拖动一根参数曲线时，若每次都重建控件树，
   会把"只改了一个值"的代价放大成"重建整个面板"。TuneLab 的 `ViewRefreshScheduler`
   把这条做成两级脏位，正是为了这个。

### 6.3 性能与一致性的冲突点（需要明确取舍的地方）

有两处性能和一致性天然冲突，**必须在设计时就定下来，不能留给实现者临场判断**：

**① 拖动中的暂停（`Suspended`）**
拖动时如果每次变化都重算并重绘，会打断交互手感；但完全不算，用户又看不到实时反馈。
TuneLab 的取舍是：**拖动期保留脏位、跳过 flush，但标脏照常累积**，松手时一次补上。
**取舍理由**：交互流畅度 > 实时预览精度，但**不能丢数据**（脏位保留）。

**② 曲线绘制不追求"数学精确"，只追求"像素上一致"**
逐像素采样意味着放大到极高倍率时，曲线形状会从"平滑"变成"折线"（因为采样点就那么多）。
TuneLab 的取舍是**采样点数 = 可见像素数**，即"一个像素一个采样点"——
在这个精度下，多余的点本来就是看不见的。**不要为了"精确"去增加采样密度**，
那是拿性能换不存在的视觉收益。

## 7. 落地顺序（建议）

1. **先定 `ViewportRequest` / `ViewportPayload` 两个结构 + 三种图层的 payload 形状**。
   这是接口契约，定错了后面全要返工。
2. **把"求值"全部收到核心层**——特别是 `Tick2X` 类的换算和 `effective` 类的判据。
   只要有一处求值漏在 UI 层，边界就不成立。
3. **接 `RefreshScheduler`**（两级脏位 + Suspended）。先不做脏区收窄，用保守口径（全量重算）跑通。
4. **再加脏区收窄**（`AnchorDirtyRange` 那套）。这一步是纯优化，可以在 3 正确之后再上。
5. **最后上峰值金字塔分级**。这是数据侧最重的一块，但它可以独立测试
   （同一段音频，不同缩放级别下取出的峰值序列应当互相一致）。

**第 3 步和第 5 步的顺序不要颠倒**：调度器的正确性靠"重算结果对"就能验证，
金字塔分级则要额外验证"各级之间一致"。先让系统在简单实现下正确，再引入分级缓存。

## 8. 与 TuneLab 的差异清单（v3 需要额外解决的）

前面引用的都是 TuneLab 已跑通的机制，但**它们能成立有一个前提：同进程**。v3 跨了边界之后，
下面这些是**新增成本**，需要单独设计：

| 项 | TuneLab（进程内） | v3（跨边界）需要补 |
|---|---|---|
| 句柄生命周期 | GC 管，持旧引用安全 | 需显式引用计数或代际回收——否则核心侧改了没人知道 UI 还拿着 |
| 异常传播 | 调用边界 catch 即可 | 协议要有错误帧；且要区分"求值失败"与"协议失败" |
| 时序 | 同步调用，天然有序 | 需 `Generation` 序号丢弃过期回答；需定义消息全序或说明允许乱序的部分 |
| 取消 | 直接不调了 | 需显式 cancel 帧（长计算要被后续请求打断） |
| 回压 | 天然（调用即阻塞） | 若 UI 画不过来，核心推送会堆积——需丢弃旧帧策略 |
| 调试 | 直接打断点 | 需要协议层的 trace/重放能力，否则跨边界 bug 极难复现 |

**其中"回压"和"取消"是最容易被漏掉的两个**，因为它们在同进程版本里根本不存在——
但跨边界后，"UI 跟不上核心的推送速度"和"用户快速滚动导致前面的请求白算"
这两件事会立刻变成资源泄漏和卡顿。建议在协议第一版就把这两条的帧定义好，
哪怕实现先留空。

## 附：一句话总结

**协议层只做一件事：把"画什么"从核心送到 UI，用不可变快照 + 版本号，按可见视口裁剪，
按一拍合并。**

三条不可妥协的纪律：

1. **发布即不可变，变化时换引用**（§1.1）——所有跨边界数据的前提。
2. **订阅回调只标脏、不读数据**（§4.2）——所有一致性问题的解药。
3. **求值一律在核心层，UI 只接收与渲染**（§0）——边界成立的唯一条件，
   漏一处就地失效。
