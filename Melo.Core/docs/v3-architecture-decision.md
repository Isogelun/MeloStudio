## 0. 先说结论

| 问题 | 结论 |
|---|---|
| **核心层与 UI 层同进程吗** | **否——核心层独立进程** |
| **核心层用什么语言** | **不限定；允许维护多个通过同一规范验收的实现** |
| **UI 层用什么语言** | **自由**（建议 C# + Avalonia 起步，随时可换） |
| 插件呢 | 独立进程 |
| 协议层有几道 | 两道，但**共用一套协议内核** |
| 音频合成走协议吗 | **不走序列化**，走共享内存 |
| UI 层能随便换吗 | **能**——这是本次架构变更带来的最大收益 |
| 每帧数据的过路费 | **固有代价**，靠共享内存降到最低 |

### 1.1 三个进程

│                      │    │                      │    │                      │

### 1.2 关键结构特征

**核心公共契约与语言无关。** Rust、C++、C#、Go、Zig 等实现均可存在，客户端通过同一协议连接，
工程文件也保持互通。单个实现可以自行选择单语言或 FFI；语言专用 ABI 不得成为公共契约，
每个实现都必须通过同一套语义、协议和实时性能验收。

**UI 和插件在协议这一层是平权的**——两者都是"连核心进程的客户端"。这个对称性很干净：
新增一类客户端（Web 端、移动端、CLI）不需要改架构，只需要实现协议。

### 1.3 与原始 v3 图的差异

原始图上画了**三**道"中间层 通信协议层"。本方案做两处修正：

**修正一：把「插件接口 / 引擎接口」从协议层里摘出来。**

那一栏**不是协议层，是契约声明**——定义"插件要实现哪些能力"，不是"双方交换什么消息"。
把契约和协议混在一个概念框里，会导致实现时不知道该在哪一层做版本管理。

**修正二：剩下两道协议层共用一套协议内核。**

核心 ↔ UI 和核心 ↔ 插件都是跨进程，性质相同。可以共用消息框架、序号、取消、
回压、错误帧（写一遍两处用），只是**通道配置不同**：

| | 核心 ↔ UI 通道 | 核心 ↔ 插件通道 |
|---|---|---|
| 主要数据 | 绘制数据（峰值、折线、矩形） | PCM 音频 + 控制指令 |
| 频率 | 每帧（60fps） | 音频块级（每几毫秒） |
| 延迟要求 | 一帧内（16ms） | 硬实时 |
| 大数据走哪 | 共享内存 + 固定布局 | 共享内存环 |
| 控制走哪 | JSON | JSON |

## 2. 边界判据：一条线怎么画

**这是整份架构里最关键的一个判断。** 画错了，整个分层就白做。

### 2.1 判据

> **这份数据是否需要"求值"才能得到？**

| 类别 | 需要求值吗 | 归属 | 理由 |
|---|---|---|---|
| 波形峰值、参数曲线折线、音符矩形 | **要** | 核心层算完再给 | 依赖音频样本、曲线插值、tempo 换算 |
| 缩放、滚动、像素↔tick 换算 | 不要 | **UI 层** | 纯当前视口的函数 |
| hover 高亮、拖拽预览线、光标 | 不要 | **UI 层** | 纯 UI 瞬时状态 |
| 轨清单、量程、颜色 | 不要 | 核心层**（仅结构变化时推）** | 声明期就定了 |
| 锚点、音符本体 | 不要 | 核心层**（同时是编辑入口）** | 就是数据本身 |

### 2.2 为什么这条判据不能松

如果让 UI 层把"播放 / 调度 / 撤销重做 / 保存加载导出"也当数据接过来渲染，
协议层会立刻退化成**远程过程调用总线**——那就不是渲染协议了。

> **协议层只传"画什么"，不传"怎么画"，也不传"帮我做件事"。**

写操作另有一条通道，与读操作不混用同一种消息。

### 2.3 一条新出现的注意点：tick 换算分家

旧方案里 `TickAxis`（像素↔tick 换算）纯属 UI 层。**新架构下两侧都要用 tick 域**：

- **核心侧**：算求值区间、脏区收窄，全部在 tick 域里做
- **UI 侧**：像素↔tick 换算，纯渲染需要

**所以两侧各有一份缩放参数的副本，必须通过协议同步。**
否则会出现"UI 以为在看第 100-200 拍，核心以为 UI 在看第 90-190 拍"——
这类不一致的表现是画面偏移或数据错位，排查起来很隐蔽。

## 3. 各层决策与理由

### 3.1 决策一：核心层独立进程，实现语言自由

**决定**：核心层是独立进程，不指定首选语言，允许维护多个等价实现。

**理由**：

**① 语言与框架解耦。** 这是本次架构变更的核心收益。核心层不跟任何 UI 框架绑在一起，
可以自由选择最适合音频/数值计算的语言。

**② 实时约束可以由每种实现分别证明。** 音频线程的停顿是音频软件的真实痛点。

> **TuneLab 的对照**：TuneLab 核心层是 C#，音频线程必须靠**非托管内存 + 池化缓冲**
> 来规避 GC 停顿。无 GC 的实现少一个停顿来源；有 GC 的实现也可以通过预分配、池化和
> 非托管缓冲满足约束。最终以回调截止时间和欠载测试判断，不按语言名称判断。

**③ 协议把语言差异封在进程内。** 峰值金字塔要控制内存布局，多线程重算要避免数据竞争，
但各语言可以用不同机制实现；对外只暴露固定线格式和可观察语义。

**④ 多客户端成为可能。** 核心层独立后，UI 只是"客户端之一"。将来做 Web 端、
移动端、远程控制，都是"再写一个客户端"，不是"重做项目"。

**代价**（详见 §5）：

- 每帧数据要过路费（跨进程 + 共享内存 memcpy）
- 调试难度上一个台阶（需要 trace/重放）
- 协议成为唯一契约，需要自建版本闸门
- 三进程生命周期管理
- TuneLab 已跑通的机制要在每个候选实现中重写并接受同一组测试

### 3.2 决策二：UI 层语言自由，起步建议 C# + Avalonia

**决定**：UI 语言不做架构约束。**建议起步仍用 C# + Avalonia。**

**理由**：

架构上 UI 语言已经自由（因为跨了进程，不共享数据结构）。但"能换"不等于"该换"：

- 卷帘这类高频自绘，Avalonia 的 `DrawingContext` 性能足够
- 已有 TuneLab 的成熟参考实现（`AutomationRenderer` 等）
- Rust 的 UI 框架（egui / iced / slint）做音频编辑器卷帘仍不如 Avalonia 顺手

**这恰好说明架构的价值**：现在**不必为了"将来可能换"而提前换**——
协议隔开之后，将来真想换随时能换，成本是"写一个客户端"。

### 3.3 决策三：音频不走序列化

**决定**：跨进程协议分两条通道——控制消息走消息通道，PCM 音频走共享内存环。

**理由**：音频合成是实时的。一次合成可能吐几 MB，逐块走 JSON/protobuf 编解码，
延迟抖动会直接变成爆音。

> **来自 TuneLab 的实证**：`IVoiceSynthesisEngine` 的契约注释写明
> `VoiceSourceInfos` "**必须立即返回、不得阻塞**——宿主与 UI 同步读取、无异步等待"。

**建议**：播放引擎放在核心进程，直接独占音频设备。这样音频回调全程在核心进程内，
**一次跨进程都没有**——恰好绕开了这个架构最大的代价。

### 3.4 决策四：UI 与插件在协议层平权

**决定**：两者都是"核心进程的客户端"，共用一套协议内核。

**理由**：

- 新增客户端类型不改架构（CLI、Web、远程控制都是"实现协议的客户端"）
- 权限模型清晰：协议里带客户端身份，核心侧可以做差异化的授权
- 协议只写一遍

### 3.5 决策五：无界面插件的参数面板由核心转发给 UI 渲染

**决定**：无界面插件只声明"我有哪些可调项"，核心层转发这份声明给 UI，UI 渲染面板。

**理由**：**"无界面插件"这个分类存在的意义，恰恰就是"我不写界面，有人替我把参数面板搞定"。**
如果让它也走 WebView，它就和有界面插件没区别了，分类可以取消。

**与 TuneLab 的同与异**：

| | TuneLab | v3 |
|---|---|---|
| 参数声明形态 | `IControllerConfig` **对象**（C# 接口 + 类） | **自描述的标记数据**（如 `{ kind, key, min, max }`） |
| 传递方式 | 进程内，共享同一份类型定义 | 跨进程，传纯数据 |
| 渲染器选择 | 宿主 `switch` 对象类型 | UI 查 `kind → 渲染器` 注册表 |
| 新增控件代价 | **动冻结 ABI**，过 RS0016 检查 | 注册新渲染器（代价低一个量级） |

**逻辑模型完全一样**：插件说"我能调什么"，UI 决定"怎么画给你"。

**必须守住**：参数描述里**不能出现任何渲染指令**（调色板、像素坐标、动画曲线）。
一旦出现，"无界面插件"这个分类立刻失效。

**附带收益**：控件集合不再是硬绑定的。UI 遇到不认识的 `kind` 降级成只读展示即可——
**插件永远不会因为客户端升级而崩溃**。

## 4. UI 层可替换性（本架构最大的收益）

### 4.1 结论

> **新架构下，UI 层整体可替换。** 换 UI 的成本是"写一个客户端"，不是"重写项目"。

### 4.2 为什么这次成立了

**旧方案（核心层与 UI 同进程）**里，结论是"只有一半能换"——因为自绘卷帘直接读核心层的
数据结构（峰值金字塔、锚点插值、`TickAxis`），那些是**能力不是数据**，
做不成每帧上千次的 RPC。

**新架构下，核心层跨了进程，卷帘拿的是协议传来的 payload**，不再直接摸核心层内部表示。
所以绑定的那条链断了：

| UI 的组成部分 | 依赖什么 | 能换吗 |
|---|---|---|
| 自绘卷帘 / 波形 / 曲线 | 协议 payload 的格式 | **能** |
| 侧边栏 / 云端 / 设置 | 协议的数据格式 | **能** |
| 有界面插件 | 协议的数据格式 | **能** |

**全部可换——因为依赖的只剩协议一个东西。**

### 4.3 但这不是免费的

可替换性是**买来的**，货币就是 §5 里那笔每帧过路费。

| | 旧方案（同进程） | 新方案（跨进程） |
|---|---|---|
| 性能 | 零拷贝（最快） | 每帧过路费 |
| UI 可替换性 | ❌ 锁死 | ✅ 可换 |

**这笔交易值不值，取决于你要不要多端。** 见 §6.6。

## 5. 跨边界的新增成本清单

跨了进程之后，下面这些是**新增成本**，需要单独设计。
其中前两条是本次架构变更新引入的：

| 项 | TuneLab（单进程） | v3（跨进程）需要补 |
|---|---|---|
| **每帧过路费** | 零（函数调用） | **固有**：系统调用 + 通知 + 调度；靠共享内存把"序列化"这一环干掉，但不可能为零 |
| **调试 / 可观测性** | 单进程断点 | **需协议层 trace / 重放**——否则跨边界 bug 极难复现。**优先级最高的新增项** |
| **协议版本管理** | 编译期检查（RS0016） | 运行时协商，兼容分支要留 |
| 句柄生命周期 | GC 管 | 需显式引用计数或代际回收 |
| 异常传播 | 调用边界 catch | 协议要有错误帧；区分"求值失败"与"协议失败" |
| 时序 | 同步调用天然有序 | 需 `Generation` 序号丢弃过期回答 |
| 取消 | 直接不调了 | 需显式 cancel 帧 |
| 回压 | 天然（调用即阻塞） | UI 画不过来时推送会堆积，需丢弃旧帧策略 |
| 进程生命周期 | 不存在 | 三进程启动/重启/单实例保证 |
| 崩溃恢复 | 不存在（一起崩） | 核心崩了 UI 怎么办；插件崩了会话怎么重建 |

**三条最重要的**：

1. **每帧过路费**——固有代价，唯一能做的就是共享内存 + 零拷贝。
2. **trace / 重放**——跨边界后从"可选优化"变成"必需基础设施"。建议第一期就做。
3. **回压 + 取消**——同进程版本里根本不存在，跨边界后会立刻变成资源泄漏和卡顿。
   建议在协议第一版就把帧定义好，哪怕实现先留空。

## 6. 与 TuneLab 的架构对比

### 6.1 根本差异

| | TuneLab | v3 |
|---|---|---|
| 核心层与 UI | 同进程 | **跨进程** |
| 核心层语言 | **必须 C#**（绑 Avalonia 与数据结构） | **不限定，可有多个等价实现** |
| 插件边界 | 程序集边界（同进程） | 进程边界 |
| 契约保障 | 编译期（`PublicAPI.Shipped.txt` + RS0016） | **运行时（协议版本协商）** |
| 性能路径 | 函数调用（最短） | 跨进程 + 共享内存（长约 10 倍） |

**本质**：TuneLab 用**编译期约束**换运行时确定性和零拷贝；
v3 用**运行时复杂度和每帧过路费**，换语言自由、UI 自由、插件自由。

### 6.2 v3 的好处（TuneLab 结构上给不了的）

**① 核心层可以尝试多种语言实现。**

协议、工程格式和黑盒一致性套件是共同基线。各实现可以采用不同的并发、SIMD、内存和运行时策略；
实时回调是否合格由截止时间、最大延迟和欠载统计判断。这样语言选择变成可测量的工程实验，
不会提前固化为架构结论。

**② UI 语言真正自由。** 见 §4。TuneLab 的 UI 是死结——`TuneLab.GUI` 里 70 个自绘
C# 文件和核心层数据结构咬在一起。而且这条在"要不要做 Web 版"上差别巨大：
TuneLab 想加 Web 版 = 重做一个编辑器；v3 = 写一个 Web 客户端。

**③ 插件生态天花板更高。** TuneLab 插件被 12 种 `ControllerConfigs` 封死了面板能力；
v3 插件可自带界面、可用任何语言。

**④ 多客户端天然支持。** 核心层独立后，UI / 插件 / CLI / Web / 远程控制都是平权客户端。

**⑤ 崩溃隔离。** 插件崩了可单独重启。**但这条收益有限**——核心崩了 UI 基本也没用，
见下面坏处。

### 6.3 v3 的坏处（TuneLab 完全没有这些成本）

**① 每帧过路费——最实质的代价。**

TuneLab 卷帘滚动：UI 直接调 `GetPeaks()`，返回，零拷贝，直接画。**开销 = 一个函数调用。**

v3 卷帘滚动：

```
UI 发现视口变了 → 打包请求 → 序列化 → 跨进程 → 核心解码
→ 算峰值 → 写共享内存 → 发通知 → UI 收到 → 读共享内存 → 画
```

**链路长约 10 倍。** 单帧可能只多几百微秒，但拖动卷帘 / 拖动曲线 / 播放游标移动
时**每帧都走一遍**。共享内存能把序列化那环干掉，但系统调用 + 通知 + 调度躲不掉。

**② 调试难度上一个台阶。** 数据在哪个进程出的错？跨进程数据流怎么复现？
`Generation` 序号错乱导致的画面闪回怎么查？——需要 trace / 重放基础设施。

**③ 协议成为单点风险。** TuneLab 的 SDK 变更有 `RS0016` 在编译期拦住；
v3 的协议变更是**运行时才炸**（老客户端连上来才发现不兼容）。
**你得自己造一套 TuneLab 用编译器免费获得的东西。**

**④ 启动与部署变复杂。** 三进程生命周期：谁拉起谁、崩了怎么办、单实例怎么保证、
安装包带几个运行时。**纯粹的额外工作量，无功能收益。**

**⑤ 现成经验只能搬思路不能搬代码。** `ViewRefreshScheduler`、`AnchorDirtyRange`、
`Waveform` 全都要用新语言重写。数学规则和逻辑结构可以照搬（有价值），
但没有一行代码能直接用。

### 6.4 逐项对照

| 维度 | TuneLab | v3 新架构 |
|---|---|---|
| 核心层语言 | C#（被迫） | **不限定，可维护多个等价实现** |
| 音频线程 GC | 要手工规避 | **由具体实现处理，统一通过实时验收** |
| UI 可替换 | ❌ 换不了 | **✅ 换客户端即可** |
| 性能路径长度 | 函数调用（最短） | 跨进程 + 共享内存（约 10 倍） |
| 每帧过路费 | 零 | **固有** |
| 调试难度 | 低 | **高（需 trace/重放）** |
| 契约保障 | 编译期 | **运行时（需自建闸门）** |
| 插件面板能力 | 12 种控件封死 | **无上限** |
| 插件语言 | 必须 C# | **任意（走协议）** |
| 多客户端 | 不支持 | **平权客户端** |
| 进程/部署复杂度 | 单 exe | **三进程生命周期** |
| 崩溃隔离 | 无 | 有（收益有限） |
| 重写成本 | — | 已跑通机制要重写一遍 |

### 6.5 可直接借鉴的 TuneLab 经验（思路可搬，代码要重写）

| 机制 | TuneLab 位置 | 在 v3 里的形态 |
|---|---|---|
| 两级脏位调度 | `TuneLab.GUI/GUI/ViewRefreshScheduler.cs` | 在核心进程内重写一份（新语言），边沿触发 + 一帧合并 |
| 脏区收窄 ±2 相位纪律 | `TuneLab/Data/AnchorDirtyRange.cs` | 纯算法，照数学规则实现 |
| 峰值金字塔（hop=64） | `TuneLab/Audio/Waveform.cs` | 数据结构逻辑照搬 |
| NaN 作为"此处无值" | `AutomationConfig.DefaultValue` | 语义照搬，不涉及代码 |
| 发布即换引用 | `TuneLab/Data/SynthesisLock.cs` | **变形为双缓冲 + 序号校验** |

**双缓冲的具体形态**（跨进程替代"持旧引用就安全"）：

```
核心进程                           UI 进程
┌────────────────┐                ┌────────────────┐
│ 写入缓冲 A      │ ──共享内存──→  │ 读取缓冲 A      │
│ 序号 ++         │                │ 校验序号        │
│ 写下一帧到 B    │                │ 画完 A，读 B    │
└────────────────┘                └────────────────┘
```

核心层读到序号不匹配就丢弃——**这是 `SynthesisLock` 在跨进程下的对应物**。

### 6.6 结论与判据

**这个架构换来的东西值不值，取决于目标：**

**值得，如果：**

1. **真打算做多端**（Web / 移动 / 远程控制）——这是结构上唯一 TuneLab 给不了的能力
2. **音频性能是核心竞争点**——可以用统一基准比较各语言的实时表现
3. **想要开放的插件生态**——第三方能自带界面、能用任何语言
4. **需要验证不同语言的工程取舍**——协议与黑盒套件使实验结果可以直接比较

**不值得，如果：**

1. **只想做一个好用的桌面音频编辑器**——TuneLab 的路子更省心，性能还更好
2. **团队小、时间紧**——三进程 + 协议 + trace 是很大的前期投入
3. **没打算做多端**——v3 最大的那个好处用不上

> **一句话**：TuneLab 是"用编译期约束换运行时确定性和零拷贝"；
> 新架构是"用运行时复杂度和每帧过路费，换语言自由、UI 自由、插件自由"。
> **这不是谁更好，是拿"确定性和性能"买"解耦和自由度"。**

**一个降级路径**：如果对"多端"还不确定，可以先按"核心层同进程"起步，
但**把协议层预留出来**（接口按协议的形状定义，只是先走进程内直调）。
将来真要做多端时，把核心层抽出去独立进程，协议层已经在位了——
这样避免了"为不存在的需求提前付过路费"。

## 7. 语言策略

### 7.1 判据

| 层 | 关键需求 | 选择依据 |
|---|---|---|
| 核心层 | 数值性能、实时约束、并发、内存布局 | 一致性测试与目标机器基准 |
| UI 层 | 自绘性能、框架成熟度 | 框架生态 |
| 协议 | 跨语言、可调试 | 通用性 |
| 插件 | 门槛低、可复用 | 生态与模板 |

### 7.2 核心层

不设推荐语言排行榜。任何候选实现都必须满足：

1. 实现同一份协议、工程格式和领域语义，不把语言类型当作线格式。
2. 通过同一套命令、撤销、渲染、共享内存生命周期和恢复黑盒测试。
3. 在目标机器报告启动、内存、视口延迟、后台合成调度、音频回调截止时间和欠载。
4. 标注实现 ID、版本、能力与已知限制，便于客户端选择和诊断。

语言专用库只是实现细节。某语言实现可用其最合适的音频、并发和 SIMD 生态，也可以在内部使用 FFI，
但不得改变公共行为或要求其他客户端加载该语言运行时。

### 7.3 UI 层

**建议 C# + Avalonia**（理由见 §3.2）。备选：

- **TypeScript + Web Canvas**——未来 Web 版用，但卷帘性能不如 Avalonia
- **Rust + egui / iced**——技术栈统一，但 UI 生态做卷帘还吃力

### 7.4 协议层

| 组成 | 建议 | 理由 |
|---|---|---|
| 控制消息 | **JSON** | 可读、好调试、生态全。控制消息量小频低，性能不是问题。**可调试性 > 性能** |
| 大数据（绘制数据） | **共享内存 + 固定布局** | 每帧 30KB，序列化撑不住 |
| 音频 | **共享内存环 + C ABI 布局** | 硬实时，float32 平面/交错 |

**控制消息不用 protobuf** 的理由：需要 schema 编译，插件作者负担重。
**不用自定义二进制**：控制消息量小，不值得。

### 7.5 插件层

插件同样不限定语言。第一版先提供一份规范参考客户端和跨语言测试向量，之后为有需求的语言提供 SDK。
SDK 是协议的便利封装，不是能力白名单；没有官方 SDK 的语言仍可按规范实现客户端。
共享内存的字节序、对齐、原子操作与释放流程必须由每个语言桥接层通过测试。

### 8.1 已确定

- [x] 核心层独立进程，实现语言自由，允许多个等价实现
- [x] UI 层语言自由（起步建议 C# + Avalonia）
- [x] 插件独立进程
- [x] 音频合成走共享内存，不走序列化
- [x] 有界面插件自带界面（不绑定 Vue）
- [x] 无界面插件的参数面板由核心转发、UI 渲染
- [x] 两道协议层共用一套协议内核，UI 与插件在协议层平权

### 8.2 待定

- [ ] **播放引擎在核心进程还是独立音频进程？**
      建议：在核心进程，独占音频设备——音频回调全程不跨进程。
- [ ] **核心进程的启动方式**：UI 拉起？还是独立守护进程？
      影响单实例保证和崩溃恢复策略。
- [ ] **协议版本协商机制**：协议版本怎么声明、不兼容时怎么降级。
- [ ] **入口层是否要做？** TuneLab 有 agent / CLI / MCP / headless 共用一套命令面。
      新架构下这类客户端天然可加（都是协议客户端）——是暂不需要，还是列入规划？

### 8.3 下一步

1. **写协议内核的规格**——消息框架、序号、取消、回压、错误帧。
   这是 UI 通道和插件通道共用的部分，写一遍两处用。
2. **写大数据通道的规格**——共享内存布局、双缓冲 + 序号校验、生命周期管理。
3. **搭 trace / 重放基础设施**——跨边界后这是必需项，不是优化项。
4. **把 TuneLab 的四样机制用新语言重写**：调度器 → 脏区收窄 → 峰值金字塔 → 双缓冲。
   顺序按这个来（先正确再优化，细节见 `v3-render-protocol-design.md` §7）。

## 附：三条不可妥协的纪律

1. **协议层只传"画什么"，不传"怎么画"，也不传"帮我做件事"。**（§2）
   ——边界成立的唯一条件，漏一处就地失效。
2. **发布即不可变，变化时换引用。**（§6.5）
   ——跨进程下变形为双缓冲 + 序号校验，它是所有一致性方案的地基。
3. **大数据一律走共享内存，控制才走消息。**（§7.4）
   ——每帧过路费是这个架构的固有成本，共享内存是唯一能把它压住的工具。
