# Vocoder 中的特征与 Transformer：从录音到波形的完整说明

> 状态：原理说明与待实现方案。本文只讨论 vocoder 内部如何读取声音特征、生成波形。当前代码尚未加入本文描述的 Transformer。
>
> 推荐先读本文理解数据如何流动，再读 [Transformer Vocoder 评估方案](transformer-vocoder-evaluation.md)了解训练对照和验收方法。

## 1. 先直接回答：是单独提取特征，再合并吗？

**首版方案是：沿用现在的特征提取流程，得到每一帧的 72 维特征，将它们整体送入网络，再由 Transformer 结合前后帧进行处理。**

之前提到的“分组编码再合并”，是一种后续可以尝试的网络结构。它是在已经得到的 72 维特征里，取出不同字段分别处理，然后拼回同一帧的内部表示；不需要为三个分组重新分析三遍录音。

为了理解清楚，先只看首版：

```text
录音 WAV
   ↓ 现有 F0 分析器 + LLSM
每一帧的 72 个声音特征
   ↓ 归一化 + 可学习的输入投影
每一帧供网络使用的内部表示
   ↓ Transformer 参考前后帧
带有时间上下文的内部表示
   ↓ 现有卷积网络与合成参数预测头
滤波器系数、噪声增益
   ↓ 与原始特征驱动的激励一起合成
可以播放的音频波形
```

这里有四种不同的操作：**提取特征、编码特征、结合时间上下文、合成波形**。它们的输入、输出和任务都不同。

## 2. 什么是“每一帧的特征”？

录音是连续的波形采样点。分析器每隔一段时间计算一次声音的描述，这个时间位置对应一帧特征。计算一帧时通常会观察附近的一段音频；“帧移”不等于分析器只看这么短的窗口。

项目默认采样率为 48,000 Hz、帧移为 256 个采样点，所以每隔约 `256 / 48000 = 5.333 ms` 产生一帧描述。

例如，一段恰好 2 秒的音频有 96,000 个采样点，在这个时间轴上对应 375 帧。每帧有 72 个数，整段特征就是一个 `375 × 72` 的数组：

| 时间位置 | 这一帧的内容 |
| --- | --- |
| 第 0 帧 | 清浊音、F0、Rd、64 个谱编码值、5 个 BAP 值 |
| 第 1 帧 | 同样的 72 个字段，数值反映下一个时间位置 |
| 第 2 帧 | 同样的 72 个字段 |
| …… | 按原来的时间顺序排列 |
| 第 374 帧 | 最后一帧的 72 个字段 |

数组的**行表示时间**，**列表示不同特征**。72 不是帧数，也不是 72 个音符，更不是 72 份独立的录音。

当前字段定义见 [特征定义](../src/core/features.py)：

| 字段 | 维数 | 零起始索引 | 可以怎样理解 |
| --- | ---: | --- | --- |
| VUV | 1 | 0 | 是否有周期性发声；清音也可能有可听见的噪声，VUV=0 不等于静音 |
| F0 | 1 | 1 | 基频，描述周期性发声的音高 |
| Rd | 1 | 2 | LLSM 的声门模型参数，描述一部分声源特性 |
| 谱编码 | 64 | 3～66 | 声音在不同频率上的分布信息，包含发音和音色线索 |
| BAP | 5 | 67～71 | 分频带的非周期性信息，与噪声成分有关 |
| 合计 | 72 | 0～71 | 同一时刻的一组声音描述 |

这些字段不是完全互不相关的独立旋钮。谱编码不等于纯粹的歌手音色；BAP 不等于所有气声表现；Rd 也不能单独决定整段声音听起来如何。

## 3. 第一步：特征提取，发生在录音分析阶段

现有 [分析入口](../src/preprocessing/analyze.py)主要完成：

1. 用 FCPE、RMVPE 或其他已支持的后端提取并对齐 F0。
2. 把波形和 F0 交给 `pyllsm2` 分析。
3. 用 LLSM Coder 整理为每帧 72 维的特征数组。

这个流程中本来就可能存在多个分析步骤。“沿用一次分析流程”不表示所有特征来自同一个算法，也不表示只访问一次波形；它表示首版不再为新网络重新设计一套音频分析流程。

训练数据预处理时可以把这些结果保存为 `.npy`。训练和特征推理直接读取数组即可。只有从新的 WAV/FLAC 开始合成时，才需要先走音频分析入口。

**Transformer 在本方案里接收分析完成的特征，不直接接收 WAV，也不负责调用 LLSM。**

## 4. 第二步：特征编码，发生在神经网络内部

72 个数的取值尺度不同。例如 F0 用 Hz 表示，VUV 通常为 0 或 1，谱编码和 BAP 又有各自的范围。现有 `input_normalizer` 先把它们转换为适合网络处理的数值尺度；归一化所用范围属于模型配置和权重的一部分，需要在训练与推理时保持一致。

之后的 `input_proj` 是一个可学习的投影。当前实现是核长为 1 的卷积，默认把**同一帧**的 72 个数转换为 256 个内部数值：

```text
第 t 帧：72 维原始特征
          ↓ 归一化
第 t 帧：72 维归一化特征
          ↓ 可学习的输入投影
第 t 帧：256 维内部表示
```

这个投影会学习怎样组合不同字段。它不是再做一次音频特征提取，也不是凭空增加录音信息。256 只是网络内部选定的表示宽度，内部第几个数通常没有“这是 F0”或“这是气声”的固定含义。

首版直接复用这样的整体投影即可。它本身已经能够混合音高、谱形、Rd 和 BAP 信息，不要求事先拆成三个网络。

## 5. 第三步：Transformer 在时间方向上处理这些表示

经过投影，两秒音频变成 375 帧，每帧有 256 个内部数值。Transformer 的主要操作，是让每帧参考指定范围内其他帧的表示，再更新自己的表示。

可以用下面的例子理解：

```text
输入：  第 0 帧  第 1 帧  ……  第 t 帧  ……  第 374 帧
                              ↑
                    参考允许范围内的前后帧
                              ↓
输出：  第 0 帧  第 1 帧  ……  第 t 帧  ……  第 374 帧
```

输出仍然是 375 帧。第 t 帧仍对应第 t 个时间位置，只是它的内部表示结合了上下文。**不会把 375 帧压成一个平均值，也不会把它们重新排序。**

这里每个时间帧相当于 Transformer 序列里的一个单元。不同特征字段是这个单元的组成部分；首版不是把 F0、Rd 和每个谱编码值分别当成一个时间单元。

举例说，一段“啊——”逐渐变轻时，输入特征里已经记录了相关变化。Transformer 可以学习怎样结合前后帧的变化，帮助后面的网络生成更连贯的滤波器和噪声控制。这里的“参考”是训练得到的数值运算，不意味着模型知道歌词是“啊”，也不需要提供歌词标签。

我们希望它改善长音和过渡，但这不是自动发生的：过度利用上下文也可能抹平辅音、换气或快速变化。需要与原卷积模型做训练和试听对照。

## 6. 第四步：后面的模块把表示变成声音

Transformer 的输出还是一组数字，不能直接播放。它继续进入现有 `primary_wn`，再交给两个预测模块：

- `spectrum_gen`：根据隐藏状态预测三路动态 FIR 滤波器系数，用来塑造谐波、噪声和瞬态分支的声音。
- `noise_proc`：预测不同频带的噪声增益。

同时，原始特征有一条独立通路：F0 和 VUV 继续用于生成谐波激励，BAP 和 VUV 继续参与噪声强度计算。当前瞬态分支还会使用原始谱编码的变化。三路激励经过滤波、合并和 PQMF/卷积后处理，才得到最终波形。

因此，在这个设计里，Transformer 更直接影响的是**滤波和噪声参数的预测**。F0 驱动激励的机制仍然存在；但这也不保证任何训练结果都会完美保持音高，最终仍需在生成波形上检查。

同样的两秒例子，输出样点数仍为：

```text
375 帧 × 每帧 256 个采样点 = 96,000 个采样点
96,000 / 48,000 Hz = 2 秒音频
```

## 7. “分组处理，再合并”具体是什么？

这是在第 4 节的编码阶段可以尝试的另一种结构。

先从已经提取好的每一帧 72 维数组中选择字段：

```text
同一帧的 72 维特征
  ├─ F0 + VUV             → 小编码器 A → 该帧的音高相关表示
  ├─ 64 维谱编码          → 小编码器 B → 该帧的频谱相关表示
  └─ Rd + 5 维 BAP        → 小编码器 C → 该帧的声源/噪声相关表示
                                              ↓
                         拼接同一帧的三个表示，再做一次投影
                                              ↓
                               该帧的统一内部表示
```

对所有帧都这样处理，就重新得到一条按时间排列的序列，再送进 Transformer。拼接发生在**同一帧的特征维度**上，不是把三个声音片段接成更长的音频。

例如，三个编码器分别输出 32、128、32 个数，那么每帧拼接后有 192 个数，再投影为 Transformer 所需的宽度。这些维数只是解释用的例子，不是本项目已经确定的配置。

分组的价值在于给不同字段独立的处理容量，方便研究哪一类信息有效。它不能保证音高、音色和气声从此完全独立；分组后通过合并和 Transformer 仍会互相影响。它还增加了结构和实验变量，因此应等整体输入版本有基线后，再与其做对照。

| 操作 | 合并什么 | 在哪一步发生 | 时间帧数是否变化 |
| --- | --- | --- | --- |
| 提取特征 | 把分析结果组织为每帧 72 个字段 | 录音分析阶段 | 由音频长度和帧移决定 |
| 整体输入投影 | 学习组合一帧内的所有字段 | 网络编码阶段 | 不变 |
| 可选分组编码与拼接 | 拼接同一帧各组的内部表示 | 网络编码阶段 | 不变 |
| Transformer | 让每帧参考前后帧的表示 | 时间上下文处理阶段 | 首版保持不变 |
| 波形合成 | 组合谐波、噪声、滤波等结果 | 声音生成阶段 | 转换为 `T × hop` 个波形采样点 |

## 8. 首版究竟改哪里？

当前 [模型入口](../src/core/model.py)的大致结构是：

```text
原始特征 → 归一化 → 输入投影 → primary_wn → 合成参数预测
```

首版建议变为：

```text
原始特征 → 归一化 → 输入投影 → Transformer → primary_wn → 合成参数预测
```

下表给出默认 256 通道时的形状。`B` 是批次大小，`T` 是特征帧数，二者都不是声音参数。SDK 的单条 `LLSMFeatures` 保存为 `[T,72]`，会话调用模型前会补上大小为 1 的批次维度：

| 位置 | 形状 | 说明 |
| --- | --- | --- |
| 送入核心模型的特征批次 | `[B,T,72]` | 每帧 72 个有明确定义的字段 |
| 模型内部原始/归一化特征 | `[B,72,T]` | 转置便于卷积；保留原始数据供激励使用 |
| `input_proj` 输出 | `[B,256,T]` | 已有的可学习整体投影 |
| Transformer 输入与输出 | `[B,T,256]` | 首版使用按帧排列、batch-first 的编码器 |
| 送回 `primary_wn` | `[B,256,T]` | 转回卷积布局，原归一化条件仍可继续使用 |
| 波形输出 | `[B,1,T×256]` | 48 kHz 单声道音频 |

新增模块可先用两层、四个注意力头和有限时间窗口，配置成可关闭。选择 256 帧作为单层窗口时，默认跨度约 1.37 秒；多层叠加后的有效上下文可能更宽。实现时要明确窗口包含多少左帧、右帧，不能把“单层窗口宽度”误当作整个模型的上下文上限。

当前卷积本身已经会利用附近时间帧。Transformer 增加的是另一种、更灵活的上下文处理方式，是否比扩大卷积范围有效，要由实验判断。

## 9. 模型如何学会这样处理？

仍使用现有的“特征数组 + 对应原始 WAV”配对数据：

1. 将一段特征送入加入 Transformer 的 vocoder。
2. 得到模型生成的音频。
3. 与对应的真实音频比较频谱、波形和其他训练指标。
4. 根据误差更新 Transformer 及参与训练的其他网络参数。

Transformer 不需要额外的“这一帧应关注哪一帧”人工标注。注意力和内部表示由声音重建任务共同训练得到，也不需要为这轮实验准备歌词或音符对齐。

已有 `.npy` 仍可用于首版实验，因为外部特征定义没有变。但新增网络有新的权重，不能只插入未训练的 Transformer 就期待音质提高。可以从同一个已训练基模进行受控微调，也可以从头训练；两种方式都要提供相应基线。

为了观察较长上下文的作用，正式对照应包括 2 秒及更长训练片段。所有对照组使用相同的数据划分和片段长度，避免把训练片段变长的收益误算给 Transformer。训练策略与验收详见 [评估方案](transformer-vocoder-evaluation.md)。

## 10. 能解决什么，哪些事情需要另做？

| 问题 | 本方案的关系 |
| --- | --- |
| 长音音色或噪声是否能更连贯？ | 是主要待验证目标 |
| 滑音和辅音过渡能否更自然？ | 可以评估，但不能保证一定改善 |
| 是否还需要 LLSM？ | 首版仍使用它提供的 72 维特征 |
| 能否直接输入歌词或音符？ | 这需要上游声学模型，本方案没有增加此功能 |
| 能否直接替换旧 checkpoint？ | 新结构需要明确配置、加载逻辑和训练，不能直接当作原模型 |
| 输入音高错了，Transformer 会自动修复吗？ | 当前 F0 仍驱动激励，不应依赖它自动修正分析错误 |
| 能否流式输出？ | 还需设计有限前瞻、状态和分块协议；当前 SDK 返回整段结果 |
| 能否只改 F0 就任意变调且音色完全不变？ | 不能由这个结构保证，谱特征与音高仍有耦合，需要独立变调评测 |

首版的工作范围可以记作：**现有声音特征 → 更好地结合时间上下文 → 预测合成参数 → 生成波形。** 特征提取、内部编码和最终合成各自承担不同任务；“分组编码再拼接”只是内部编码的一种可选实现。
